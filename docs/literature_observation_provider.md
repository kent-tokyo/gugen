# Literature observation provider (Phase 20B)

`LiteratureObservationCorpus` (`src/literature_observations.rs`, `literature_corpus` feature) loads a gugen-native JSON snapshot of the Kononova et al. 2019 text-mined synthesis corpus -- the same corpus Phase 20A audited and `fetch_kononova.py` samples for Phase 11's holdout benchmark -- and answers exact target+precursor-set queries against it. The snapshot itself is produced by `benchmarks/build_literature_observation_snapshot.py`, regenerated by re-running that script, not hand-edited. This document is regenerated from a real local run (`cargo run --release --example literature_observation_benchmark --features literature_corpus`) after building a fresh snapshot, not hand-edited.

**No Planner connection.** No `ConditionPrecedent`, no `Planner::plan` input, no ranking/`Score01` involvement, anywhere. This is not a convention this module happens to follow -- it is structurally impossible: `ConditionPrecedent::purpose` is a required (non-optional) `HeatingPurpose`, while every `CorpusHeatingObservation::heating_purpose` is always `None` (enforced both at construction and by the snapshot schema itself, which has no field for it at all). Promoting corpus observations to `ConditionPrecedent`s is deliberately deferred to a future phase gated on a manual purpose-matching accuracy audit, which does not exist yet.

## Source

Kononova, O., Huo, H., He, T., Rong, Z., Botari, T., Sun, W., Tshitoyan, V., Ceder, G. "Text-mined dataset of inorganic materials synthesis recipes." *Scientific Data* 6, 203 (2019), DOI `10.1038/s41597-019-0224-1`.

Hosted at https://api.figshare.com/v2/articles/9722159 (DOI `10.6084/m9.figshare.9722159`), license **CC BY 4.0**, verified live against the figshare API by `build_literature_observation_snapshot.py` on every run. Raw record count: 19,488 (matches `fetch_kononova.py`'s and `audit_kononova_corpus.py`'s independently verified count).

## Final public API

- `CorpusManifest { source, release, schema_version, checksum, record_count }` -- snapshot provenance. `checksum`/`release` are informational only (gugen never has the upstream raw file to verify them against); `record_count`/`schema_version` are actively checked at load time.
- `CorpusHeatingObservation { target, precursors, route_family, heating_purpose, operation_index, temperature, duration, atmosphere, doi, corpus_record_index }` -- one reported heating operation. `precursors: BTreeSet<Composition>` (order-invariant identity). `heating_purpose: Option<HeatingPurpose>` is always `None`.
- `LoadMode::{Strict, Lenient}`, `LoadReport { accepted, duplicates_collapsed, rejected }`, `RejectedObservation { position, reason }`.
- `LiteratureObservationCorpus::load(json: &str, mode: LoadMode) -> Result<(Self, LoadReport), ProviderError>` -- no file or network I/O in the crate; the caller reads the file.
- `LiteratureObservationCorpus::{manifest, observations, len, is_empty, find_exact}`. `find_exact(route_family, target, precursors) -> Vec<&CorpusHeatingObservation>` -- exact `Composition` equality (not ratio-normalized), order-invariant precursor-set match, returns `&[]` immediately for any `route_family != ConventionalSolidState` (explicit "inapplicable," not a coincidental empty result).

## Snapshot schema

`gugen-literature-observation-snapshot-v1` (`CORPUS_SNAPSHOT_SCHEMA_VERSION`): `{"manifest": {...}, "observations": [...]}`. Each observation is `CorpusHeatingObservation`'s own serialized shape (standard serde derive for every field except `heating_purpose`, which has no wire representation at all -- `#[serde(skip)]` on the real struct, paired with `#[serde(deny_unknown_fields)]` on the internal parsing struct, so a snapshot that tries to set one is rejected outright rather than silently ignored).

## Exact matching rules

`find_exact`'s `target` match is exact `Composition` equality -- the same convention `InMemoryLiteratureConditionProvider` (Phase 10) already uses, not a normalized-ratio match. `precursors` match is exact-set equality via `BTreeSet<Composition>`, so caller-supplied precursor order never affects the result. A `Mechanochemical` query returns `&[]` unconditionally and immediately (no scan) -- the source corpus has zero evidence for any route family other than `ConventionalSolidState` (Phase 20A).

## Deduplication rules

Two observations are exact duplicates if they agree on every field except `corpus_record_index` (target, precursors, route_family, operation_index, temperature, duration, atmosphere, doi) -- the same raw record appearing more than once in the source corpus itself (a data artifact; Phase 20A's audit found 19 such record-level groups in the full 19,488-record corpus). Deduplication is order-independent: sorting by a canonical content key (with `corpus_record_index` as the final tiebreaker) before collapsing means the same set of duplicates collapses to the same surviving entries regardless of the snapshot file's row order, and the lowest `corpus_record_index` in a duplicate group always survives. **Two observations that report the same conditions but have different `doi` are never collapsed** -- they are independent literature reports and both are kept; resolving genuine multi-source agreement or conflict across them is Phase 20C, not this module.

## Corpus-wide numbers (this run)

Built from a live fetch of the full 19,488-record corpus, filtered with the identical structural-validity gate Phase 20A's audit uses (parseable target and precursors, 1-4 distinct precursors after dedup):

- Structurally valid records: 9,045 (matches Phase 20A's audit exactly)
- Records contributing at least one `HeatingOperation` observation: 7,626 / 9,045 (84.3%) -- the remaining 1,419 valid records report no `HeatingOperation` at all (e.g. mixing/grinding-only routes in the raw text)
- Records contributing 2+ observations (multi-step, e.g. calcine then sinter): 4,294
- Raw observations emitted by the build script (one per `HeatingOperation`): 13,982
- After `LiteratureObservationCorpus::load` (validation + dedup): 13,982 accepted (parsed successfully, pre-dedup -- every Python-emitted observation parsed cleanly; expected, since Python already applies the same unit/finiteness checks before writing the snapshot, and Rust's own validation is defense-in-depth, not dead code, since it runs regardless of what produced the file), 0 rejected, 13 exact duplicates collapsed, **13,969 in the final queryable corpus** (`corpus.len()`)

## Coverage

- Unique targets (exact composition, not ratio-normalized): 4,089
- Unique exact routes (target + precursor-set, exact composition): 4,896
- Unique DOIs represented: 6,370

## Condition-field coverage (per observation, not per record)

- Temperature resolved: 11,198 / 13,982 (80.1%)
- Duration resolved: 9,774 / 13,982 (69.9%)
- Atmosphere reported: 5,439 / 13,982 (38.9%) -- of those, 4,825 mapped to a structured `Atmosphere` variant (air/oxygen/argon/nitrogen/hydrogen/carbon monoxide) and 614 preserved verbatim as `Atmosphere::Controlled { description }` (an unrecognized single string, e.g. "PbO"/"thermal carbon"/"ambient"/"carbon dioxide," or 2+ reported strings for one operation)
- These are lower than Phase 20A's record-level figures (79.9%/71.1%/44.8%) for a structural reason, not a regression: Phase 20A counts "does this *record* have >=1 resolving `HeatingOperation`," while this module reports per-*operation* resolution, and a genuinely ambiguous multi-entry temperature/duration reading (see below) resolves to `None` here even when the record itself has *some* resolvable heating step elsewhere.
- Verified live against the full corpus, not assumed: 2,377 of the corpus's `HeatingOperation` entries report 2+ candidate temperature readings, and 2,311 of those (97.2%) disagree rather than repeating the same value. This module leaves a disagreeing multi-entry reading `None` rather than guessing (max value, first entry, or a union range) -- the single largest reason temperature coverage is lower here than a "just take the max" approach would report.

## Rejected observations breakdown

At the snapshot-build stage (Python, identical to Phase 20A's own filter): unparseable target 9,081; unparseable precursor 954; zero or >4 precursors after dedup 408 (19,488 total minus 9,045 valid = 10,443, matching exactly). At the Rust load stage (this run): 0 rejected -- see "Corpus-wide numbers" above for why that is expected, not unverified.

## Performance

Measured locally (`cargo run --release --example literature_observation_benchmark --features literature_corpus`), not CI-gated -- CI only exercises the small committed fixture (`tests/fixtures/literature_observation_snapshot_sample.json`, 11 entries), never the full-scale file (gitignored, regenerated locally from `build_literature_observation_snapshot.py`, never bundled into the published crate).

- **Load time**: 537 ms total for 13,982 input observations (~38 µs/observation), including manifest validation, per-observation parsing/re-validation through gugen's existing constructors, sorting, and deduplication.
- **Lookup time**: 1.61 s total across 4,896 distinct target+precursor-set queries (~328 µs/query). `find_exact` is a linear scan over the whole corpus (no index) -- documented as such in its own doc comment; total query time scales as O(queries × corpus size), which is fine for the single-target lookups `Planner`-style usage would make, but would not be for a caller issuing thousands of queries per corpus load. No index was built for Phase 20B (out of scope; revisit if a future phase's usage pattern needs it).
- **Memory**: ~9.2 MB estimated for 13,969 loaded observations (~688 bytes/observation) -- a rough capacity-based estimate (composition entries, DOI/description string storage, plus each observation's fixed-size fields), not a rigorous allocator-level measurement; no profiling dependency was added for one phase's benchmark.
- **Serialized size**: 5.3 MB input snapshot file (13,982 observations); 4.7 MB re-serializing the loaded, deduplicated 13,969 observations.

## Known limitations

- Ambiguous multi-entry temperature/duration readings resolve to `None`, never a guessed union or "first entry wins" value -- see the coverage section above. This is a real, load-bearing information loss (2,311 operations), not a rare edge case, disclosed as such rather than silently accepted.
- Atmosphere vocabulary is a fixed 6-string map to structured `Atmosphere` variants; everything else becomes `Atmosphere::Controlled { description }`, preserving text rather than asserting an interpretation (e.g. "ambient" is *not* assumed to mean "air").
- `find_exact` is a linear scan; no index is built. Acceptable at this corpus's ~14K-observation scale for single-target queries; would need revisiting for a bulk-query workload.
- No cross-record conflict resolution: a target+precursor-set pair with many independent DOIs returns all of them, unreconciled (Phase 20C, not built).
- No promotion path to `ConditionPrecedent`/`Planner` exists yet (by design -- see the module doc comment and this document's opening paragraph).
- 1,419 of the 9,045 structurally-valid records contribute zero observations (no `HeatingOperation` reported at all in the source text) -- not a bug, a real property of the underlying corpus.

## What this document does not establish

Not a claim that any observation here is *correct* for planning a real synthesis -- gugen never independently re-verifies a text-mined paper's own extraction accuracy (that is Phase 20D, a manual audit against original papers, not built here). Not a claim about `HeatingPurpose` -- none is ever inferred, by design. Not a performance guarantee for a workload this module wasn't measured against (e.g. thousands of queries per load, or a corpus release with meaningfully different scale or vocabulary than the one measured here).
